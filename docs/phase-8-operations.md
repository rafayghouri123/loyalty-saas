## Billing and administration

Publish actual paid plan versions in `/admin/plans`; amounts are integer paisa, strictly positive. All offered plans include the agreed launch features. Existing subscriptions and invoice snapshots retain their published economics. Trial duration defaults to 14 days; configurable grace defaults to seven. Billing boundaries use the original Asia/Karachi calendar anchor, including month-end and leap-day clamping. The first paid interval starts at trial end; renewal invoices are issued seven days before interval start and due at start.

Use `/admin` to record actual payment instructions, canonical provider IDs, approved financial/audit retention and purchased backup/Storage expiry coverage. Missing commercial inputs remain visibly unconfigured. Do not replace them with synthetic test values. Settings changes require support capability, AAL2, recent authentication and a recorded reason. Billing reconciliation and plan publication independently require billing capability.

Owners submit evidence at their invoice page. A validated private screenshot is optional and never settles payment. An authorized billing administrator must reconcile the actual bank/provider record, attest it, and enter the exact invoice amount and canonical provider/reference. No partial payments or inferred success from screenshots. Confirmation is idempotent, subscription-locked, and globally deduplicated by normalized method/provider/reference. Late or out-of-order payment covers the recorded interval. The correction action appends one compensating event at the original positive amount, reopens its invoice and recomputes access without altering another paid interval or any loyalty balance.

Permitted plan changes require a current paid invoice with matching price/billing interval and financially compatible future invoices. Published invoice snapshots remain immutable. A lower limit preserves excess existing records and blocks additions. Price/interval changes require an agreed renewal; this release does not invent mid-period proration or silently reprice an issued invoice. Owners can contact the configured support email for a plan change and cancel renewal with confirmation. Cancellation takes effect at the recorded paid/trial period end without further grace.

Support sessions require reason, explicit Configuration/Transaction support scope, 15/30/60-minute expiry and recent MFA. Read/end operations verify the current admin and its own unexpired grant, and audit each action. Support data excludes customer contacts and does not impersonate an owner. Job recovery is limited to safe database/artifact workflows; uncertain provider sends cannot be blindly retried. Suspension stops new enrollment/earning/marketing while preserving balances, card/history access, issued benefit fulfillment and audited reversals.

## Persistent worker and monitoring

`Dockerfile.worker` compiles the independent worker on pinned Node 24.21.0, installs production dependencies, runs as the non-root `node` user and has a bounded health check. `compose.worker.yml` adds process supervision, init, 45-second graceful shutdown and bounded logs. Docker is unavailable on this workstation; CI includes a Linux image build. A supplied host must verify the image and supervision before acceptance.

Create an ignored `.env.worker` using secret-store values: `APP_ENV=staging`, `WORKER_DATABASE_URL` (restricted worker session-pooler login), `WORKER_DB_SSL=true`, CA PEM/base64, Supabase URL, Storage service key and the shared encryption ID/key. Set `EXPORT_PROCESSING_ENABLED=true` and `PRIVACY_PROCESSING_ENABLED=true` for artifacts and Auth deletion. Media processing requires its separate flag. Keep push/email flags disabled until deliberately verifying those services. Mount the Firebase secret file only on the worker; never bake it or `.env*` into the image. All remote DB connections retain certificate verification.

The worker schedules hourly billing and daily retention, in addition to the existing source-ledger reconciliation. Privacy/export outbox enqueue and dispatched marking remain atomic. The worker rechecks authoritative scope and expiry at execution. Unexpected failures retain durable jobs/receipts and produce fixed-label redacted logs.

`scripts/monitor-worker.mjs` runs in a separate supervised service, polling every 30 seconds. It checks DB availability, heartbeat older than 30 seconds, >100 pending events or oldest >5 minutes, >=5 failed/unknown provider attempts in 15 minutes, >=1,000 active hourly email-ingress attempts, ledger discrepancies, missing/stale (>26-hour)/failed backup and missing restore evidence. These thresholds are operational defaults, not proof of load capacity. Auth bucket observation covers the application's persisted email ingress; Google/provider-side abuse and hosting budget alerts additionally require provider monitoring.

Set a real private HTTPS `MONITOR_WEBHOOK_URL` and optional token. Discord incoming webhooks are detected automatically: messages include fixed alert labels/time and explicitly cleared labels, disable mentions and require `wait=true` plus a matching saved message ID/content before acknowledging delivery. No separate Discord bearer token is sent. Generic destinations retain the JSON payload and optional `MONITOR_WEBHOOK_TOKEN`. Discord 429 responses permit at most two bounded retries; unsuccessful delivery does not advance observation state. Destination URLs/tokens and exception details are never logged. [Discord webhook contract](https://docs.discord.com/developers/resources/webhook).

Alerts send initially, on change and once per hour while unresolved, including recovery; recovery can retain unrelated warnings. DB unavailability cannot imply that DB-backed warnings cleared. `--once --dry-run` prints safe observations without sending. Run `test:monitor` for offline regression checks. With `APP_ENV=staging` explicitly set, `verify:monitor:discord` sends two clearly labeled acceptance messages using an isolated refused DB probe followed by a real staging query, then reads both saved messages back from Discord. It does not stop the hosted worker or alter health records. The destination is saved only in ignored `.env.local` on this workstation; configure it through the chosen host's secret store for continuous operation.

Discord failure and recovery delivery passed on 2026-09-27; safe receipt/evidence identifiers are recorded in [acceptance](phase-8-acceptance.md). The local command is an acceptance probe. The user subsequently selected a separate [Vercel monitor](vercel-monitor.md), now deployed and verified with five-minute automatic checks, a narrow health-only login and a daily watchdog. A monitor on the same host detects process failure; use an independent external liveness/readiness probe for host/network death. In-memory deduplication resets on restart, so a restart sends a fresh observation.

## Privacy and retention

Customer account settings offer requester-scoped export/deletion; membership preferences offer relationship deletion. Exports stream keyset pages into numbered JSON parts <=3 MiB, plus a manifest with all section counts and no 10,000-record cap. Current consent, enrollment, balances/history, personal notifications/manual content, staff identity, own payment submissions/audit and privacy requests are included. Other people's data, private cafe configuration, credentials/tokens/bearer secrets are excluded. Parts are private and expire at the original 24-hour request deadline. Every download verifies current requester identity both before and after bounded fetch; no signed URL reaches the browser. Failed uploads are recorded before Storage writes so orphan cleanup can find them.

Whole-account deletion requires recent sign-in and is blocked for active owners until audited ownership transfer/closure resolves responsibility. Relationship deletion erases contacts/name, consent, personalized scheduled/manual content and handles/intents, while retaining the private account link and financial history. Whole deletion removes that link, clears profile/birthday/staff/device identity, revokes Auth sessions and deletes the Auth identity through the provider. Completion is recorded only after provider deletion succeeds. If it fails after DB anonymization, stale sessions already fail; an authorized fresh-MFA support recovery resumes the original request. Do not claim total erasure: ledger, minimal audit/enrollment proof and backup copies remain according to approved policy.

Configured operational defaults are notification/attempt/manual content 90 days, logs 30 days, referral visits 90 days, inactive bindings 90 days and temporary uploads/exports 24 hours. Immediate deletion scrubbing takes priority over timed cleanup. No timer deletes loyalty ledger, balances, invoices or payment events. Support must supply the actual financial/audit policy and backup expiry before production. Host log rotation and monitoring retention also need the configured policy; the database job cannot purge an external vendor's logs.

## Backup and restore procedure

Target RPO <=24 hours and RTO <=4 hours must be validated against purchased services. Record the provider plan, backup frequency, last completion, retention expiry, encrypted off-provider copy locations, Storage object coverage, encryption-key recovery and responsible operators. Supabase's DB backups exclude Storage bytes; back up and restore objects separately. [Supabase backup documentation](https://supabase.com/docs/guides/platform/backups).

Keep a current privacy/consent/device revocation journal outside the DB snapshot, protected as sensitive data with access/expiry controls. Continuously preserve completed deletion records (`customerId`, `kind`, nullable `membershipId`), consent withdrawals (`membershipId`, `channel`, `purpose`) and revoked/invalid device IDs. Record journal checkpoints and test access during incidents. DB backups alone cannot recover requests made after their timestamp. Auth/provider settings, Storage configuration and application encryption keys also require separately controlled recovery. [Supabase project-cloning limitations](https://supabase.com/docs/guides/platform/clone-project).

1. Stop all worker senders, external triggers and manual message opens. Keep messaging disabled in the restored environment. Identify an approved recovery point and preserve the damaged DB/object set for reconciliation.
2. Restore into an isolated destination. Restore DB, private/public Storage bytes and access policies, Auth settings and keys. Check hashed object manifests, immutable payment/ledger totals, balance reconciliation and requester/tenant isolation. Measure elapsed time from recovery authorization, not just a file copy.
3. Replay the external journal with operator-only `app_private.restore_privacy_replay(requests_json,consents_json,devices_json)` before any sender. It anonymizes restored identities/contacts, revokes devices/staff/Auth, marks matching old deletion requests complete, and rejects active-owner blockers. Repeating is safe. Resolve each blocker through audited ownership recovery; do not ignore it.
4. Revalidate actual Supabase Auth identity/session behavior in the destination. Confirm withdrawn consent and revoked generations prevent old queued campaigns/automations and manual opens. Audit uncertain provider attempts; do not blindly resend them. Scan bundles/logs and verify private storage/exports.
5. Record the real recovery point, loss window, timing, DB/object counts and privacy replay result. Set backup/restore checks from this evidence. Start the supervised worker with messaging initially disabled, reconcile durable queues and inspect errors, then explicitly enable approved senders after privacy and idempotency checks pass.

`test:restore` is a real local PostgreSQL 18.4 stopped physical copy and isolated restore, with preserved immutable payments/ledger/purchases and a separately hashed synthetic object. It completes a real account deletion **after** the backup, saves its journal outside the snapshot, and verifies replay removes the restored pre-deletion identity/contact and stops the old pending deletion from resurrecting state. It also replays consent/device revocations twice. This exercises the procedure, but is not a hosted Supabase backup purchase, Storage backup integration or deployed RPO/RTO claim. Evidence stays under ignored `.local/restore-evidence/`.
