## Execution and isolation

`monitoring/vercel` is a small standalone Next application with the pinned stable Workflow SDK. Every **five minutes**, a bounded step queries fixed health status and probes the real web origin's `/api/health/ready`. It closes the DB pool, checks the saved alert state and sends Discord messages initially, on change and hourly while unresolved. Discord must confirm the matching saved message; delivery failure does not acknowledge the new state. Recovery names the cleared checks while retaining unrelated warnings. Network and SQL exception details, credentials, customer records and response bodies are excluded from logs and Workflow state. HTTP ambiguity can repeat a delivered notification; this is at-least-once delivery.

The Workflow sleeps durably between checks, without holding a Function or DB connection. After 288 checks it releases its singleton hook and starts a child run carrying the last acknowledged labels/time. A project-scoped, non-public `createHook` token permits only one ordinary monitor run to execute checks. Concurrent or replayed handoffs can create inert duplicate runs, but only the hook owner checks/sends. Public webhook resumption is disabled. Stale runs check hook ownership before observation. Hook handoff and HTTP delivery have brief transition windows, so this is not a strict exactly-once alert guarantee.

`GET /api/control` is a protected daily watchdog. It retains the current deployment's running hook owner, otherwise cancels an obsolete owner and starts the deployed monitor. A permanent Workflow failure can wait until the next daily watchdog; this is not a monitor for the monitor. The operator can run `node scripts/control-vercel-monitor.mjs ensure` after deployments or rollbacks. To stop monitoring persistently, set `MONITOR_ENABLED=false` in this project and redeploy; cancellation alone does not disable future Cron starts.

Migration **061** creates the non-login `loyalty_monitor` role with only public-schema usage and execution of `worker_health_status()`. The separately generated `loyalty_monitor_login` inherits this role. Real staging and regression checks verify that customer profile reads, outbox updates and worker controller execution are denied, with no superuser/bypass-RLS privileges. No worker, migration, Auth, Storage, encryption or customer credentials are deployed to this project.

## Deployment and controls

Configure the monitor project's production target with `APP_ENV=staging`, `MONITOR_ENABLED=true`, `MONITOR_DATABASE_URL`, `WORKER_DB_SSL=true`, inline `DATABASE_CA_CERT_PEM`, private `MONITOR_WEBHOOK_URL`, `MONITOR_APP_ORIGIN=https://loyalty-saas-three.vercel.app`, and a distinct random `CRON_SECRET` of at least 32 characters. `vercel.json` uses `sin1`, 120-second Workflow Functions and a daily watchdog. The control endpoint checks the full bearer secret with timing-safe comparison and returns private/no-store replies. Public root returns only the service label. Unsigned Workflow executions and public singleton-hook resumption are denied.

The account is Hobby. Ordinary Cron can run only daily, so Workflows supplies the five-minute cadence. This is a deliberate change from the alternative daemon's 30-second polling. About 8,640 checks in 30 days create roughly 43,200 normal step/sleep events plus handoff/watchdog/retry overhead. This is an estimate, not a billing guarantee, and does not establish that the combined worker/monitor fits the account's allowance. The worker's ten-second polling already exceeds a full month's Hobby allowance. No plan purchase or upgrade was performed. [Cron limits](https://vercel.com/docs/cron-jobs/usage-and-pricing), [Workflow metering](https://vercel.com/docs/workflows/pricing).

For a fresh checkout, run `npm ci --prefix monitoring/vercel`, `monitor:test`, and `monitor:build` using the pinned runtime. The build copies the canonical `scripts/monitor-delivery.mjs` into an ignored shared file, runs production/type compilation and verifies actual executable step registration. `scripts/prepare-vercel-monitor.mjs` creates a curated ignored upload directory and source SHA-256 manifest using the saved project metadata; it excludes credentials, environment files and local dependencies. The existing app/worker project is not redeployed by these commands. Rebuild/redeploy this monitor after canonical delivery changes.

With the saved operator secret, `POST /api/control?action=verify` runs a bounded, clearly labeled staging-only failure/recovery probe. It observes an actual connection refusal against an isolated local probe, then real staging health and web readiness; it does not stop the worker or change health rows. `POST /api/control?handoff=test` verifies three ten-second checks and then hands off to the ordinary five-minute run. Both require the secret and `APP_ENV=staging`. `scripts/verify-vercel-monitor.mjs` verifies protected routes, actual Workflow execution, saved Discord messages and handoff. Its `--steady` mode observes two automatically scheduled checks without invoking the monitor. Evidence and operator secrets remain ignored under `.local/`.
